# خطة تنفيذ الفروع (Branches) والتوسع — Mindlytics

هذا المستند يجمع **الخطوات التنفيذية** الحالية واللاحقة، ويربطها بما تم بناؤه في الكود. يُحدَّث مع كل مرحلة.

## ما تم تنفيذه الآن (المرحلة 1)

1. **جدول `branches`** في قاعدة البيانات: تعريف فرع (اسم، slug للـ subdomain، دومين مخصص اختياري، دولة، منطقة زمنية، عملة، حالة، ألوان/شعار، ملاحظات داخلية، إعدادات JSON).
2. **لوحة الإدارة**: مسارات CRUD تحت `admin/branches` مع واجهات عربية.
3. **السايدبار**: قسم **«الفروع والامتداد»** يضم قائمة الفروع، إضافة فرع، وصفحة توضيحية «خطة الفروع» (قراءة هذا المستند من المتصفح للتجربة السريعة).

**تشغيل الهجرة:**

```bash
cd Mindlytics && php artisan migrate
```

**بذور الصلاحيات (اختياري):** إن كنتم تستخدمون `PermissionsSeeder` للصلاحيات المسماة `manage.*`، شغّلوا:

```bash
php artisan db:seed --class=PermissionsSeeder
```

تُضاف صلاحية `manage.branches` (للاستخدام لاحقاً مع سياسات أدق؛ مسارات الإدارة الحالية محمية بـ `role:admin|super_admin`).

## المرحلة 2 — ربط البيانات بالفرع (`branch_id`)

### ما تم

**المستخدمون (سابقاً)**

1. عمود **`users.branch_id`** + فرع **`main`** عند الحاجة + تعبئة المستخدمين الحاليين.
2. علاقة **`User::branch()`**، وتعيين تلقائي عند **`creating`** عند غياب `branch_id`.
3. واجهات إدارة المستخدمين (اختيار فرع + عرض + صفحة الفرع بعدد المستخدمين).

**الطلبات والمالية والتسجيلات (هذه الخطوة)**

4. أعمدة **`branch_id`** في الجداول: **`orders`**, **`student_course_enrollments`**, **`invoices`**, **`payments`** (مفتاح أجنبي → `branches`).
5. **تعبئة تلقائية**: من `users.branch_id` حيث وُجد `user_id`؛ للمدفوعات تُكمَل من الفاتورة أو الطلب إن لزم؛ ثم تعيين الفرع الافتراضي لأي صف متبقٍ.
6. عند الإنشاء في التطبيق:
   - **`AssignsDefaultBranchOnCreate`** على `Order`, `StudentCourseEnrollment`, `Invoice`.
   - منطق مخصص في **`Payment::creating`** (مستخدم → فاتورة → طلب → افتراضي).
7. **`QueriesByBranch`**: نطاق `forBranch($id)` على النماذج أعلاه + **`User`** (للفلاتر والتقارير لاحقاً).
8. **`Branch`**: علاقات `orders`, `studentCourseEnrollments`, `invoices`, `payments`؛ وصفحة عرض الفرع تعرض أعداد هذه الكيانات.

**الهجرة:** `2026_05_14_130000_add_branch_id_to_orders_enrollments_invoices_payments.php`

**الهجرة (محافظ ومعاملات):** `2026_05_14_140000_add_branch_id_to_wallets_and_transactions.php`

### ما تم (محافظ ومعاملات + دومين)

9. أعمدة **`branch_id`** في **`wallets`**, **`transactions`**, **`wallet_transactions`** مع تعبئة من المستخدم / الدفع / الفاتورة / المحفظة ثم الفرع الافتراضي.
10. تعيين تلقائي عند الإنشاء في النماذج المذكورة (`creating`).
11. **المرحلة 4 (جزء):** Middleware **`ResolveBranchFromHost`** في مجموعة `web` (في بداية المجموعة): يطابق `custom_domain` أو `{slug}.دومين_APP_URL`، ويضع **`BranchContext`** في الحاوية و`view()->share('resolvedBranch', …)`. مسارات محجوزة في **`config/branches.php`**. يُستثنى من الحل: `admin`, `api`, `community`, `employee`, `storage`, إلخ.
12. **`AppServiceProvider`**: تسجيل افتراضي لـ `BranchContext` (فرع فارغ) للـ CLI وغير الطلبات التي تتخطى الـ middleware.

### ما تم (كورسات متقدمة + باقات + أوفلاين + كاش الدومين)

13. **`advanced_courses.branch_id`** + نطاق **`visibleOnCurrentHost`** + إدارة الفرع في إنشاء/تعديل الكورس المتقدم؛ فلترة المسارات العامة و`/courses` و`/course/{id}` والباقات.
14. **`offline_courses.branch_id`** (تعبئة من مدرب → `users.branch_id` ثم الافتراضي) + نفس النطاق للعرض العام؛ حقل فرع في إدارة الكورس الأوفلاين؛ مجموعات الحجز العامة تفلتر حسب فرع الكورس.
15. **الباقات العامة**: `whereHas` + `withCount` على كورسات نشطة ومرئية للفرع الحالي؛ صفحة `/package/{slug}` لا تعرض باقة بلا كورس مرئي على ذلك النطاق.
16. **كاش مطابقة المضيف**: `config('branches.resolve_cache_ttl')` (افتراضي 3600 ثانية، `0` يعطّل) في **`BranchResolver`**؛ إبطال تلقائي عند **`saved` / `deleted`** على **`Branch`**.
17. سمة **`VisibleOnCurrentHostScope`** المشتركة بين `AdvancedCourse` و`OfflineCourse`.

### التالي

1. استخدام **`resolvedBranch`** في القوالب العامة (شعار/ألوان/تذييل) بشكل موحّد.
2. **Global scope** أو سياسات عند إدخال دور «مدير فرع» (`branch_manager`) مع تقييد الاستعلامات.
3. ربط **`offline_course_groups`** أو **`packages`** بـ `branch_id` إن احتجتم باقات/مجموعات حصرية لكل فرع دون الاعتماد على الكورسات فقط.

## المرحلة 3 — المستخدمون ومدير الفرع

1. ~~`users.branch_id`~~ — مُنفَّذ كأساس (nullable + افتراضي عند الإنشاء).
2. **دور `branch_manager` + لوحة `/branch-office`** — مُنفَّذ: إنشاء المدير من صفحة الفرع في الإدارة (`POST admin/branches/{branch}/branch-managers`) مع عرض كلمة المرور لمرة واحدة؛ لوحة مخصصة (إحصاءات + قائمة مستخدمي الفرع) مع ربط **`BranchContext`** بفرع المستخدم واستثناء المسار من حل الدومين بالمضيف.
3. منع تغيير `branch_id` من واجهات غير مصرح بها (تدقيق إضافي على مستوى السياسات لاحقاً).

## المرحلة 4 — الدومين وواجهة الأكاديمية

1. ~~**Middleware** `ResolveBranchFromHost` + `BranchResolver` + `BranchContext`~~ — مُنفَّذ كأساس (انظر أعلاه).
2. ~~ربط المحتوى العام (كورسات، باقات، أوفلاين) بفلترة **`branch_id`**~~ — مُنفَّذ كأساس (انظر المرحلة 2 أعلاه).
3. توجيه/نطاقات فرعية كاملة في DNS وSSL للدومينات المخصصة.
4. **كاش Redis**: يمكن توجيه `CACHE_STORE=redis`؛ منطق **`BranchResolver`** يستخدم `Cache` الافتراضي.

## المرحلة 5 — المركز (HQ) والرقابة

1. لوحة تقارير عبر الفروع (فلاتر `branch_id`).
2. **سجل تدقيق** مع `branch_id` للعمليات الحساسة.
3. **Impersonation** آمن لدعم الفروع (اختياري).

## المرحلة 6 — التوسع والصيانة

1. فهارس DB: `(branch_id, created_at)` حسب أنماط التقارير.
2. Read replica للتقارير الثقيلة عند الحاجة.
3. تخزين ملفات ببادئة `branch_id/` على S3-compatible.
4. مراقبة و structured logs مع `branch_id`.

## المرحلة 7 — الامتثال الدولي

1. تقييم **data residency** لكل دولة؛ عند اللزوم: نشر إقليمي + DB منفصل مع تكامل مركزي للتقارير.
