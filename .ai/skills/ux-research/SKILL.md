# UX Research

Before inventing UI, understand the learner job.

## Research modes (practical)

1. **Codebase archaeology** — current student routes, dashboards, drop-offs, empty states
2. **Jobs to be Done** — what progress the student hires Mindlytics to make
3. **Friction audit** — where motivation dies
4. **Hypothesis writing** — what change should move engagement/completion
5. **Success metrics** — how we will know it worked

## Student jobs (defaults)

- Know what to do now
- Feel progress quickly
- Recover after falling behind
- Prepare for quizzes/exams with confidence
- Get intelligent help without leaving flow

## Friction catalog

Look for:

- Admin-dashboard cognitive load
- Too many equal cards / no priority
- Weak Arabic hierarchy
- AI buried or chatbot-shaped
- Progress invisible
- Dead empty states
- Mobile RTL breakage

## Output template

```markdown
## Learner problem
[One sentence]

## Evidence
- [route/view/behavior/log/insight]

## Job to be done
When [situation], I want to [progress], so I can [outcome].

## Hypothesis
If we [change], then [metric] will improve because [reason].

## Experience implication
Section question answered: [one of the five dashboard questions]
```

## Rules

- Prefer real Mindlytics constraints over imaginary personas
- Research should narrow UI — not expand feature soup
- Every finding must translate to a section question or removal
- Do not use research theater to justify template dashboards

## Checklist

```
UX Research Progress:
- [ ] Map current experience
- [ ] State JTBD
- [ ] List top frictions
- [ ] Write testable hypothesis
- [ ] Tie to dashboard questions / metrics
```
